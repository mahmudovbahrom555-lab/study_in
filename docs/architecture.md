# Архитектура проекта

## Общая схема

```
┌─────────────────┐         ┌─────────────────┐
│  Flutter App    │ ──────► │   Go Backend    │
│  (iOS/Android)  │ ◄────── │   (REST API)    │
└─────────────────┘  HTTPS  └────────┬────────┘
                                     │
                ┌────────────────────┼────────────────────┐
                │                    │                    │
                ▼                    ▼                    ▼
        ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
        │  PostgreSQL  │    │    Redis     │    │    MinIO     │
        │  (данные)    │    │  (кеш, сесс) │    │   (файлы)    │
        └──────────────┘    └──────────────┘    └──────────────┘
```

## Backend — Clean Architecture

```
┌─────────────────────────────────────────────┐
│  Presentation (HTTP handlers)               │  ◄── Внешний слой
├─────────────────────────────────────────────┤
│  Application (Services / Use Cases)         │
├─────────────────────────────────────────────┤
│  Domain (Entities, Business Rules)          │  ◄── Ядро
├─────────────────────────────────────────────┤
│  Infrastructure (PostgreSQL, S3, FCM)       │
└─────────────────────────────────────────────┘
```

**Правило зависимостей:** внешние слои зависят от внутренних, никогда наоборот.

### Поток обработки запроса

```
HTTP Request
   │
   ▼
Middleware (auth, logging, recovery)
   │
   ▼
Handler (HTTP-специфика, парсинг)
   │
   ▼
Service (бизнес-логика)
   │
   ▼
Repository (интерфейс)
   │
   ▼
PostgresRepository (реализация)
   │
   ▼
PostgreSQL
```

## Принципы

### Обязательные

1. **UUID везде** — никаких автоинкрементов в публичных API
2. **Stateless API** — JWT, без сессий в памяти
3. **Soft delete** — `deleted_at` вместо физического удаления
4. **Timestamps** — `created_at`, `updated_at` на всех таблицах
5. **Зависимости через интерфейсы** — для тестируемости
6. **Один файл = одна ответственность**

### Рекомендуемые

1. **Тесты на критичную логику** — оценки, тесты, посещаемость
2. **Структурированные логи** — slog в Go, dev.log в Flutter
3. **Контекстные ошибки** — обёртывание `fmt.Errorf("operation: %w", err)`
4. **Async-задачи через очередь** — push, email, отчёты — не блокируют HTTP

## Стратегия масштабирования

### Вертикальная (на первых этапах)

До 1000-5000 пользователей — один сервер CX22/CX42 в Hetzner справляется.

## Безопасность

1. **JWT с коротким TTL** — access 15 мин, refresh 30 дней
2. **Refresh токены в БД** — можно отозвать
3. **SMS rate limit** — 1 раз в минуту с номера
4. **Signed URLs для файлов** — TTL 1 час
5. **HTTPS обязательно** — через Caddy в продакшене
6. **Аудит-лог критичных действий**
7. **Соль для всех хешей** — bcrypt для будущих паролей

## Расширение без переписывания

Новая возможность добавляется новым модулем и парой строк подключения. Существующий код не переписывается.

### Новая фича — новый модуль

**Backend:** `internal/features/<name>/` — `handler.go` (`RegisterRoutes`), `service.go`, `repository.go` (интерфейс), `dto.go`. Реализация хранилища — `internal/infrastructure/postgres/`, таблицы — новая миграция. Подключение — одна строка `RegisterRoutes` в `server.go`.

Модули не импортируют друг друга. Если модулю нужны чужие данные, он объявляет узкий интерфейс, а адаптер пишется в `server.go` (пример: `groupMemberAdapter` для `parents`).

**Flutter:** `lib/features/<name>/{data,domain,presentation}`. Подключение:
- маршруты — в `core/router/app_router.dart`;
- вкладка главного экрана — запись в `_tabs` (`home_shell.dart`) с ролями, которым она видна;
- вход со страницы группы — плитка в `_QuickActions` (`group_detail_page.dart`).

### Включение без релиза в стор: `GET /api/v1/app-config`

Публичный эндпоинт, приложение читает его на заставке и кэширует (без сети — последний ответ).
- `min_version` (`APP_MIN_VERSION`) — ниже этой версии приложение показывает «Нужно обновить приложение» и дальше не пускает.
- `features` (`APP_FEATURES=quizzes,...`) — включённые фичи. Новая фича выкатывается выключенной: ключ в `Feature` (`core/remote_config/remote_config.dart`) и проверка `isEnabled` там, где она появляется в интерфейсе. Включение — переменная окружения на сервере, без нового релиза.

Флаги пока общие для всех. Если понадобится включать фичу только тестировщикам — добавить флаги пользователя в ответ `/me`, формат `features` тот же.

### Совместимость со старыми версиями приложения

Версии из стора живут месяцами, поэтому:
- В `/api/v1` изменения только **добавляющие**: новые поля, эндпоинты, значения перечислений. Поля не удаляются и не переименовываются.
- Клиент терпим к новому: неизвестные поля игнорирует, отсутствующие берёт по умолчанию, неизвестное значение перечисления показывает нейтрально (пример: неизвестный тип уведомления — значок колокольчика).
- Ломающее изменение: сначала выпустить новую версию приложения, потом поднять `APP_MIN_VERSION`. Или сделать новый эндпоинт (`/api/v2/...`) рядом со старым.

### Языки

- **Flutter:** файл `core/localization/arb/intl_<код>.arb` и строка в `appLanguages` (`locale_resolver.dart`). Переключатель языка и `supportedLocales` строятся из этого списка.
- **Сервер:** код в `domain.SupportedLanguages`. Ограничения в БД нет, миграция не нужна.
- Язык профиля на сервере всегда равен языку интерфейса (`languageSyncProvider`: после входа и при смене языка). По нему сервер пишет push и SMS на языке пользователя.

### Задуманные фичи (не реализованы, только место в архитектуре)

- **Геолокация ребёнка для родителя.**
  - Модуль `location`. Доступ проверяется через `parent_links` (уже есть).
  - Явное согласие ученика, хранить только последние дни.
  - Вкладка «Карта» в `_tabs` для роли `parent`, за флагом.
  - Google Play: фоновая геолокация требует отдельной декларации и проверки — заложить время.
- **Чат / обсуждения тем (практика speaking).**
  - Модуль `chat`. Первая версия — REST и push (FCM уже подключён).
  - Мгновенная доставка — WebSocket-эндпоинт в том же API с Redis pub/sub между экземплярами сервера (Redis уже есть), API остаётся stateless.
  - Голосовые сообщения — через модуль `files` (MinIO).
  - Google Play для общения пользователей требует жалоб, блокировки и модерации.
- **События между модулями.** Когда модуль должен реагировать на чужое событие (оценка → уведомление, пропуск → push родителю, сообщение → push), вводится внутренний издатель событий. Сервис публикует событие (`GradePosted`), подписчики регистрируются в `server.go`, сервис-источник о них не знает. Заранее не вводим — появится с первой задачей уведомлений (аудит, P1).

## Что НЕ делаем сейчас

Чтобы не усложнять MVP, осознанно откладываем:

- Микросервисы (модули могут стать отдельными сервисами потом)
- Kubernetes (Docker Compose достаточно)
- Kafka / event sourcing
- CQRS
- GraphQL (REST проще для MVP)
- gRPC (HTTP+JSON ясен и достаточен)

Эти технологии нужно добавлять только тогда, когда боль их отсутствия станет реальной.
